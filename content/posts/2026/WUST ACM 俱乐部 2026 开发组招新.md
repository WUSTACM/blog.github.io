## 写在前面

::quote
刚开始接触开发时，很多问题都很具体：环境装不上，终端不会用，报错看不懂，Git 命令也总是记混。有人写过不少算法题，却没有完整做过一个项目；也有人对开发很感兴趣，只是一直不知道该从哪里开始。这些情况都很正常。

下面的任务从配置环境开始，慢慢过渡到阅读代码、调试程序、使用 Git 和参与协作。任务完成得快慢不会成为唯一的判断依据。我们也会关注你遇到了什么问题、尝试过哪些方法，以及能不能讲清楚自己的代码。

即使这次没有加入俱乐部，希望你仍能留下一个可以继续维护的小项目、一份完整的 README，以及一段真实的 Git 提交记录。
::

## 开始前需要什么

 编程语言没有限制，C、C++、Java、Python、JavaScript 等都可以。建议具备以下基础：

::card-list
- 掌握任意一种编程语言的基本语法；
- 了解变量、条件、循环、函数、数组或容器等基本概念；
- 能够阅读简单的报错信息；
- 愿意自己配置开发环境、查找资料并尝试解决问题；
- 注册 GitHub 或其他 Git 托管平台账号；
-  每周能抽出大约 4～6 小时。
::

遇到暂时不会的内容很正常。任务中允许查资料、向他人请教，也允许合理使用 AI。比“第一次就做对”更重要的是留下尝试、修改和思考的过程。

## 我们希望你在过程中学会什么

完成任务后，你不一定要成为某个方向的“熟练开发者”，但应该能做到：

::card-list
1. 独立配置并使用基本的开发环境；
2. 主动查找资料，读懂报错并尝试定位问题；
3. 完成一个规模适中的小任务；
4. 写出较清晰的代码和文档；
5. 使用 Git 记录修改，并通过 Pull Request 参与协作；
6. 解释自己写下或提交的代码。
::

::alert{type="warning" title="AI 使用说明"}
最后一点很重要。我们允许使用 AI，但你必须能够解释、修改和调试最终代码，并对它负责。
::

## 任务安排

### 第一阶段：配置环境和工具

#### 任务 1：搭建开发环境

选择一种自己想使用的编程语言，完成以下内容：

- 安装 VS Code 或其他编辑器；
- 安装对应的语言环境；
- 创建并运行第一个程序；
- 使用终端进入项目目录并运行程序；

---

#### 任务 2：熟悉命令行

尝试在终端中完成创建、复制、移动和删除文件等操作，并理解下面这些常用命令的作用：

```bash
pwd
ls
cd
mkdir
touch
cp
mv
rm
```

Windows、macOS 和 Linux 使用的命令可能不完全相同。尝试记录自己使用的系统、对应命令，以及一次实际操作过程。

---

#### 任务 3：完成一次 Git 协作流程

你可以参考 GitHub Skills 的入门教程，也可以直接使用俱乐部提供的招新练习仓库。

需要完成：

1. 创建 GitHub 账号；
2. Fork 或克隆练习仓库；
3. 在本地创建自己的分支；
4. 在指定目录添加个人文件；
5. 至少完成 3 次有意义的 commit；
6. 将分支推送到远程仓库；
7. 创建 Pull Request；
8. 根据评审建议至少修改一次；
9. 合并后删除不再使用的分支。

比较清楚的提交信息，例如：

::folding{title="查看提交信息示例"}
```text
docs: 添加个人介绍
feat: 完成待办事项添加功能
fix: 修复空输入导致程序退出的问题
```

尽量避免这样的提交信息：

```text
改了一下
111
最终版本
最终版本2
```
::

 Git 会保存项目的修改历史，GitHub 方便大家共同维护代码。Pull Request 中可以讨论某次修改，也可以在合并前发现问题。把这套流程完整走一遍，比单独记住几个命令更有用。

### 第二阶段：尝试开发

#### 任务 4：阅读并修改已有代码

俱乐部会提供一个约 50～100 行的小程序，其中会放入一些常见问题，例如：

- 变量名称含义不清楚；
- 相同代码重复出现；
- 程序中存在一个简单 Bug；
- 某个小功能还没有完成；
- 输入错误时程序会异常退出。

从下面的内容中选择至少两项：

- 找出并修复一个 Bug；
- 增加一个小功能；
- 调整变量名或函数名；
- 将重复逻辑整理成函数；
- 增加错误输入处理；
- 写一份简短的程序流程说明。

如果拿到的是命令行待办事项程序，可以尝试增加删除任务、标记完成、保存到文件等功能，也可以处理输入编号不存在的情况。

::alert{type="tip" title="修改之前"}
修改之前先运行一次原程序。弄清楚它现在能做什么，再开始动代码。
::

---

#### 任务 5：复现并修复一个 Bug

俱乐部会提供一个存在错误的程序。请按照下面的过程完成调试：

1. 复现错误；
2. 找到能够稳定触发错误的输入；
3. 使用输出语句、日志或调试器定位问题；
4. 修复错误；
5. 说明错误产生的原因；
6. 增加一个测试，确认问题不会再次出现。

---

#### 任务 6：为项目写一份真正能用的 README

 README 建议包含：

::folding{title="README 参考结构"}
```markdown
# 项目名称

## 项目介绍
## 已实现功能
## 环境要求
## 运行方法
## 使用示例
## 项目结构
## 遇到的问题
## 后续计划
## AI 使用说明
```
::

完成后可以和另一位同学交换项目：只阅读对方的 README，不询问本人，尝试把项目运行起来。如果没有成功，再根据遇到的问题修改文档。

一份好的 README 不是为了补齐提交材料，而是让第一次接触项目的人也知道它是什么、怎样运行、出了问题去哪里找原因。

### 第三阶段：协作

#### 任务 7：提交一份 Issue

实际使用俱乐部提供的小程序，提交一个 Bug 或功能建议。Issue 建议包含：

::folding{title="Issue 参考结构"}
```markdown
## 问题或需求
## 使用环境
## 复现步骤
## 实际结果
## 预期结果
## 截图或日志
## 建议方案
```
::

请尽量提供能够帮助他人复现和判断问题的信息，而不是只写“程序打不开”或“这里有问题”。

---

#### 任务 8：评审一次 Pull Request

每位同学至少阅读并评审一次其他人的代码。评论不要只停留在“可以”“没问题”或“写得不错”，至少提出一条具体、能够执行的意见，例如：

- 变量名没有体现它的用途；
- 相同逻辑出现了多次，可以提取为函数；
- 输入为空时可能出现异常；
- README 中缺少依赖安装命令；
- 可以补充一个失败情况的测试。

一条比较完整的评论可以这样写：

```text
这里在输入为空时会访问 s[0]，可能导致程序异常。
建议在访问前增加 empty() 判断，并补充一组空输入测试。
```

提出意见时请对事不对人，说明原因，代码评审的目的，是让参与者一起把项目做得更好。 评审时请把问题说清楚，也说明修改建议背后的原因。语气保持礼貌，因为每个人都可能漏掉细节，同时评审也能让项目多一次检查的机会。

### 第四阶段：拓展与表达

#### 任务 9：读懂一个开源仓库

选择一个规模适中的开源项目，尝试找到：

1. README 在哪里；
2. 源代码入口在哪里；
3. 项目使用什么许可证；
4. 如何安装依赖；
5. 如何运行项目；
6. Issue 区主要在讨论什么；
7. 最近一次 commit 修改了什么；
8. 一条内容清楚的 commit message；
9. 一个自己能够理解的 Pull Request。

不要求立刻为大型开源项目贡献代码。先学会在陌生仓库里找到入口、理解结构，已经是一项很有价值的能力。

---

#### 任务 10：把模糊需求拆成任务

给出一个比较模糊的需求：

> 做一个 ACM 俱乐部报名系统。

请把它拆成可以逐项完成的任务，例如：

```markdown
- [ ] 设计报名信息字段
- [ ] 制作报名页面
- [ ] 检查必填项
- [ ] 保存报名数据
- [ ] 让管理员查看报名列表
- [ ] 支持按方向筛选
- [ ] 导出报名数据
- [ ] 编写运行文档
```

在此基础上继续思考：

- 哪些是必须先完成的基础功能；
- 哪些可以作为后续扩展；
- 哪些任务能够并行；
- 哪些任务存在前后依赖；
- 如果只有一周，应该先完成什么。

---

#### 任务 11：正确使用 AI

让 AI 协助实现一个小功能，并尝试保留以下内容：

1. 自己使用的提示词；
2. AI 给出的代码或方案；
3. 运行后发现的问题；
4. 自己修改了哪些地方；
5. 使用什么方法进行验证；
6. 最终代码与初始方案有什么差别。

检查代码时，可以留意：

- 引用的库是否真实存在；
- 代码能否正常编译或运行；
- 有没有遗漏错误处理；
- 是否符合原始需求；
- 是否引入了安全问题；
- 一个简单功能有没有被写得过于复杂。

AI 给出的内容可以作为参考方案。代码提交到仓库以后，提交者需要理解它，也需要承担检查和维护的责任。

请记住：

::alert{type="warning" title="请记住"}
> AI 生成的是候选方案，提交者对最终代码负责。
::

## AI 使用说明

 招新任务允许使用 AI，但希望大家把它当作辅助学习和开发的工具，而不是替自己完成全部思考。

下面这些做法不能接受：

- 直接提交自己完全不理解的完整项目；
- 无法解释项目的核心代码；
- 隐瞒主要由 AI 完成的部分，伪装成独立完成；
- 遇到追问时只能再次依赖 AI，无法自己修改或调试；
- 将他人的项目简单改名后提交。

如果使用了 AI，请在 README 或任务记录中简要说明用在了哪里、采纳了哪些内容、自己做过哪些修改。披露 AI 使用情况不会成为负面因素，真正重要的是你是否理解并验证了提交的结果。

## 提交和提问

任务尽量通过 Git 提交。每次 commit 处理一件相对明确的事情，提交信息写清修改内容。

遇到困难时，可以把下面这些信息整理好再提问：

::card-list
- 你想完成什么；
- 当前出现了什么现象；
- 完整的报错信息；
- 已经尝试过哪些方法；
- 相关代码或截图。
::

问题很基础也可以问。把问题描述清楚，往往已经完成了一半的排查。

## 最后

 招新期间，大家可以边做边问，也可以和其他同学交换项目、互相评审。希望这段经历能帮你迈过开发中的几个小门槛，并留下一个愿意继续做下去的项目。

希望你在这段时间里认真做过、遇到过问题、解决过一些问题，也能留下一个以后愿意继续完善的项目。我们期待在代码和交流中认识你。
